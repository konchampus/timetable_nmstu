# Развёртывание — инструкция, не выполненный запуск

Production vices-prod не изменён. Бот коллоквиума не остановлен, DNS/HTTPS и BotFather не менялись. Ни одна приведённая команда не запускалась. До публичного запуска нужны разрешённые проверки и отдельное подтверждение переключения.

## Предварительные условия

- Домен с действующим HTTPS через существующий reverse proxy сервера. FreeDNS даёт DNS, не хостинг и не сертификат.
- Docker Compose v2 либо эквивалентное окружение Python 3.12+/Node 22/PostgreSQL16+.
- Отдельная PostgreSQL БД. Compose намеренно не создаёт и не публикует БД автоматически: её размещение, диск, backup и доступ определяются после инвентаризации vices-prod. БД доступна приложению по приватной сети/firewall, не из интернета.
- Два DB пользователя: runtime companion_app без DDL/superuser и отдельный companion_migrator для миграций. Для НОВОЙ выделенной БД есть [SQL подготовки ролей](<deploy/provision.sql>); не применять к общей БД существующих сервисов.
- Внешнее защищённое окружение приложения, пример без секретов — [шаблон](<deploy/backend.env.example>). Файл вне git, права 0600 и владелец deploy-оператор. Пароли в DATABASE_URL URL-encode; не передавать токены в аргументах команд, чат или журнал.
- Отдельный migration.env с теми же необходимыми параметрами, но DATABASE_URL использует роль миграций. Образ не должен содержать ни один секрет.
- На сервере должен быть свободен loopback-порт 18080; при занятом выбрать другой после инвентаризации, а не завершать чужой процесс.

## Необходимый этап фиксации зависимостей

Прямые зависимости зафиксированы в [frontend manifest](<frontend/package.json>) и [Python requirements](<backend/requirements.txt>). При восстановлении найдены существующие [npm lock](<frontend/package-lock.json>) и [Python hash-lock](<backend/requirements.lock>). [Frontend Dockerfile](<frontend/Dockerfile>) использует npm ci, [backend Dockerfile](<backend/Dockerfile>) — pip --require-hashes. Это не результат аудита или доказательство совместимости.

После явного разрешения установки/проверок: сверить существующие lock-файлы с manifest и целевыми Linux/Python 3.12, выполнить изолированную установку, обновить уязвимые версии и согласованно перегенерировать locks, выполнить аудит и закрепить Docker image digests. Считать текущие версии прошедшими аудит нельзя. Не устанавливать зависимости в личные глобальные окружения.

## Порядок запуска после разрешения

1. Read-only инвентаризация SSH через существующий alias vices-prod, только ключ. Прочитать SSH config и существующие инструкции. Никаких паролей в диалог.
2. Записать идентификаторы старого бота, команды старта/остановки, маршруты proxy, места хранения и backup. Сделать восстанавливаемую копию до любых изменений.
3. Подготовить новую БД/роли/backup. При использовании SQL подготовки передать COMPANION_APP_PASSWORD и COMPANION_MIGRATION_PASSWORD через защищённый environment механизм оператора; значения не включать в команды и не печатать результат. SQL не меняет пароли существующих одноимённых ролей.
4. Подготовить внешние backend.env и migration.env, новые токен/домен; ALLOWED_ORIGINS и ALLOWED_HOSTS точные. Runtime роль не должна запускать миграции. Пример selector переменных — [.env.example](<.env.example>), значения не секреты, но реальные env-файлы в проект не копировать.
5. После фиксации зависимостей собрать образы, затем применить начальную миграцию отдельной ролью:

       docker compose build
       docker compose --profile maintenance run --rm migrate

Миграционный head теперь включает [0002_note_source](<backend/alembic/versions/0002_note_source.py>): nullable ссылка заметки на исходное расписание, без угадывания старых связей и без удаления текста. Эта миграция в текущей сессии не применялась. Нельзя запускать новый backend на старой схеме до отдельно разрешённого upgrade.

6. Запустить ТОЛЬКО новый API/web/worker до polling при необходимости изолированной проверки; рабочий polling с новым токеном не запускается без разрешения на подключение к Telegram. Согласованный запуск:

       docker compose up -d api web worker
       docker compose up -d bot

7. [Compose](<compose.yaml>) публикует только web на 127.0.0.1:18080. API и БД не публиковать наружу. Внешний proxy должен сохранять исходный Host (иначе backend его отклонит). TLS и HSTS — на внешнем HTTPS proxy. Не включать X-Frame-Options DENY: Mini App должен открываться в Telegram Web.
8. Авторизационный IP rate limit за текущим inner proxy намеренно видит общую proxy identity (forwarded headers отключены); это безопасный, но консервативный лимит. Для масштабного запуска отдельно настроить доверенную цепочку внешнего proxy и реальный IP, принимая заголовки только от точных доверенных proxy. Никогда не включать forwarded-allow-ips=* или доверять произвольному X-Forwarded-For. До этого массовые одновременные входы могут получить 429.
9. Выполнить отдельно разрешённые функциональные/конкурентные/security проверки, включая миграцию и восстановление копии, Telegram Android/iOS/Web/Desktop. Полная матрица — [спецификация](<spec.md>).
10. Настроить Main Mini App/menu button URL в BotFather безопасно. После успешной приёмки согласовать точный cutover. Только затем остановить конкретную старую службу. Не удалять её код/данные.

Polling-бот — ровно одна реплика. Несколько API/worker возможны благодаря DB-блокировкам/lease/outbox, но должны пройти реальную конкурентную проверку. Указанные ограничения CPU/RAM в Compose — начальные бюджетные значения, не обещание производительности на неизвестном vices-prod.

## Откат и резервные копии

- Сначала остановить только новые bot/worker, вернуть старую службу и её proxy-маршрут по записанному плану. Не выполнять docker compose down -v или drop database.
- Новую БД не стирать при откате; новые заметки и прогресс должны сохраниться.
- Перед каждой последующей миграцией отдельная backup/restore точка. Начальная downgrade удаляет таблицы: это разрушительное действие, не штатный rollback приложения.
- pg_dump → потоковое шифрование в выбранное хранилище (например, age) только ключом/recipient из credential store, без временного открытого дампа в web-root. Копии вне контейнеров, отдельные права, проверка восстановления в изолированную БД. Автоматическое расписание backup здесь не создавалось.
- Предлагаемый срок backup — 30 дней, логи — 14 дней; оператор утверждает и реализует retention до публичного запуска. Docker local log ротация ограничивает объём, но не заменяет временной retention.

## Наблюдаемость и ограничения

/api/health — liveness, не readiness БД. Бот /status доступен только ADMIN_IDS и показывает состояние источника/очереди без заметок и секретов. Отдельно контролировать worker heartbeat, возраст кэша и задержку очереди. Логи access/query отключены, ошибки не содержат payload. Приложение не отправляет личные данные сторонней аналитике.

Сервис не заявлен безопасным для production до выполненной приёмки. Отсутствие runtime-проверок, dependency lock/audit, токена, домена и инвентаризации — открытые условия запуска, не скрытые «готово».
