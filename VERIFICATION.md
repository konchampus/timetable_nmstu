# Статус приёмки: автоматические suites НЕ запускались

После отдельного разрешения выполнены сборка и запуск на zerox-prod. После жалобы на поиск разрешены живые обращения с ПК/сервера и к развёрнутому адаптеру: АВб-26-2 — 30 занятий, Коробков — 26 нормализованных занятий, обе недели. Подтверждены HTTPS/API health, runtime-права БД и меню Telegram. Это не полная приёмка; детали — в [DEPLOYED_ZEROX](<DEPLOYED_ZEROX.md>). Прежний план ниже относится к этапу до этого разрешения.

В текущей сессии по инструкции владельца тесты, установка зависимостей, сборка, миграции и открытие приложения не выполнялись. Работы ограничены чтением и изменением исходников. Найдены существующие lock-файлы и Python-окружение; точная история команд прежней сессии недоступна, поэтому её результаты не приписываются этой работе. Ниже план отдельно разрешённой приёмки; актуальные изменения — в [статусе](<IMPLEMENTATION_STATUS.md>).

## Подготовленные regression suites

- [Детерминированные правила](<backend/tests/test_engine.py>): 12 игр в каталоге, точное округление, слоты, диапазоны кости, монетка, зоны/спортивные исходы, рулетка с нулём, колесо, тузы/natural/закрытые карты, сапёр и рыбалка.
- [Инварианты PostgreSQL](<backend/tests/test_database_invariants.py>): конкурентный same-key бонус/раунд, один дебет/одна выплата, payload mismatch, отсутствие утечки чужого раунда, отрицательный баланс и старый principal после delete/recreate.

DB suite по умолчанию skip. Для выполнения нужны одновременно COMPANION_ENABLE_DB_TESTS=1 и COMPANION_TEST_DATABASE_URL на ПУСТУЮ локальную БД с именем, оканчивающимся _test. Разрешены hosts 127.0.0.1/localhost/postgres-test. Suite сравнивает реальный engine URL с test URL, отказывается от заполненной БД, создаёт и затем удаляет только тестовую схему приложения в этой специально выделенной БД. Не использовать production credentials. Это metadata-based suite, а не проверка Alembic migration — миграция проверяется отдельно.

После разрешения и подготовки изолированного окружения, из backend:

    python -m unittest discover -s tests -p 'test_engine.py'
    python -m unittest discover -s tests -p 'test_database_invariants.py'

Команды выше НЕ выполнялись, результатов/процента покрытия пока нет.

## Ещё обязательные проверки

1. Сборка TypeScript/Vite, Python imports/type/schema compatibility; обновление уязвимых зависимостей и полный transitive lock/hash; контейнеры read-only/nonroot.
2. Alembic upgrade на пустой выделенной БД и сравнение metadata; восстановление backup; реальные runtime роли без superuser/DDL и сетевые границы БД.
3. API/Telegram auth: HMAC, tamper, future/expired auth_date, reordered replay, истечение/revoke, передача чужих IDs, delete против нового initData и старой in-flight операции. Ошибки/логи не выдают секреты/заметки.
4. Настоящая многопроцессная нагрузка (не только coroutine): несколько API/worker, одинаковые/разные ключи и устройства; дедлоки/timeout и потерянный HTTP-ответ после commit; баланс согласован с ledger, карты/мины не утекли.
5. Состояние клиента: same-key восстановление после закрытия WebView, 401/429/retry_transaction, смена account_generation, неактуальный баланс, исчезнувший active round, stale401 не сбрасывает свежую сессию.
6. Парсер: минимум 2 группы/подгруппы и 2 преподавателя, обе недели, общий поток, дни без пар, неоднозначные canonical URL, пустой/ошибочный/изменившийся HTML, robots/429/403, большие ответы. Проверять готовый парсер, а не просто доступность сайта.
7. Время: начало/конец, перерывы, воскресенье, граница source week после понедельника 05:00, календарные будущие даты, телефон в другом часовом поясе. Не выдумывать каникулы/фактическое местоположение.
8. Уведомления: все категории, тихие часы через полночь, пауза, смена группы/версии, /mute из обоих UI, blocked bot, worker lease/fencing, restart после sending. Невозможность гарантировать exactly-once Telegram документирована.
9. Notes: idempotent create после lost response, optimistic conflict, поисковая пагинация, чужой ID, XSS-текст, выход с несохранёнными изменениями, повторное создание удалённого request_id как описанное ограничение.
10. Браузер и реальные Telegram Android/iOS/Desktop/Web: светлая/тёмная тема, маленький экран/крупный текст, safe areas, фокус/клавиатура, reduced motion, звук после жеста/выключение/фон, WebGL unavailable/context loss, реальные FPS и освобождение ресурсов при повторном входе в игры.
11. Внешний HTTPS proxy: Host/CORS/CSP/frame-ancestors, настоящая доверенная IP-цепочка, отсутствие публичных API docs/БД/backups, error payload limits, отсутствие персонального CDN/browser cache.

## Уже исправлено в статическом review

- Доступ старого токена к новому аккаунту с тем же Telegram ID после удаления: generation + повторная проверка той же auth session под User lock.
- Восстановление старого игрового intent после delete/recreate: ключи включают generation, purge после подтверждённого удаления.
- Потеря retry intent при 401/transient DB409: envelope сохраняется.
- Исторический баланс idempotent response не выдаётся за текущий; новые платные действия требуют fresh wallet.
- Пропавшие из списка active игры сверяются отдельным GET, а не остаются активными навсегда.
- Старый in-flight401 не должен сбрасывать более новую клиентскую сессию.
- Успешное создание заметки не зависит от следующего GET; повтор создания использует один request_id.

## Дополнительные сценарии после восстановления 16.11.2026 — НЕ запускались

- Два worker с разными системными часами: lease проверяется по PostgreSQL; late finish после expiry не меняет задачу. Forbidden от старой отправки после delete/recreate не блокирует новый аккаунт.
- Медленный поиск теряет lease, новая реплика публикует результат: старый ответ не перезаписывает кэш/каталог. Изменение порядка ссылок преподавателей не создаёт новый смысловой hash.
- Применение [миграции ссылки заметки](<backend/alembic/versions/0002_note_source.py>) поверх первой миграции и на пустой БД. Старые заметки сохраняются с неизвестной связью. Исчезнувшая пара, неизвестный и устаревший снимок различаются; группа пользователя не подставляется вместо исходной группы заметки.
- Поиск по предмету/заголовку/тексту за пределами первой страницы, фильтр ДЗ, переключение запроса при запаздывающем ответе. Повтор POST после потерянного ответа посылает прежний request_id и неизменные поля. PUT после уже применённой операции может дать version conflict: текст остаётся в редакторе.
- [Журнал очков](<frontend/src/games/Ledger.tsx>): доступ двух пользователей, пагинация, суммы и balance_after, отсутствие raw event/idempotency key. StrictMode, unmount и потеря сети не должны оставлять вечную загрузку.
- /game coin, dice, roulette и прочие ссылки открывают нужную сцену с допустимым начальным выбором, не делают ставку автоматически. Запрос личных сообщений вызывается только нажатием пользователя; signed allows_write_to_pm не подменяется initDataUnsafe.
- Анимации промежуточных ходов карт/мин, показ мин только после терминального серверного результата, попадание/промах мяча, нейтральный звук возврата. WebGL fallback, reduced motion и экономичный режим сохраняют доступность управления.
- Docker backend устанавливает hash-lock; вложенные env/keys/backups не попадают в build context. Lock-файлы требуют проверки на целевой платформе и аудита.

Статические исправления перечислены как изменения кода, не как пройденные runtime-тесты. Критические/высокие найденные проблемы блокируют публичный выпуск до исправления и подтверждения.
